# 결제 완료 주문의 추가 짐·청구·수납

## 확정 정책과 범위

2026-10-30 사용자 승인 정책: 기존 짐의 원래 기간·단가·할인율은 그대로 보존한다. 각 추가 배치는 추가일 당일부터 원래 수령 예정일까지 양끝을 포함한 자체 보관일수로 계산하며, 그 일수의 장기 할인율을 독립 적용한다. 예를 들어 기존 1~5일, 추가 3~5일이면 각각 5일·3일이다. 추가가 여러 번이면 각 배치의 기간·단가·할인과 수납 근거를 불변 저장한다.

단가·할인율은 기존 Worker `src/services/pricing.ts`를 재사용한다. 캐리어 800엔/일, 백팩 500엔/일, 같은 추가 배치 안의 캐리어+백팩 세트 1,200엔/일이다. 기존 짐과 다시 묶어 원래 요금을 소급 변경하지 않는다. 7·14·30·60일부터 장기 할인 5·10·15·20%를 적용하며 JST 일수는 `storage.ts`를 쓴다. Flying Pass 정액 할인은 주문에 한 번 적용하므로 추가 배치마다 공제하지 않는다. BLACK의 기존 전체 무료 규칙은 추가 배치에도 적용하며 0엔 청구에 가짜 수납행을 만들지 않는다.

지원 대상은 정상 요금 근거가 확인되는 결제 완료·미수령 원주문이며 기존 미수납이 없어야 한다. 기존 연장 주문, 수동 금액, 미확정 환급, 최종 마감된 날짜, 원래 수령일을 지난 추가는 사유와 함께 차단한다. 21시부터 다음 날짜가 자동 연장 대상으로 잡히는 기존 규칙을 보존하고, 원래 수령일 21시 이후에는 당일 추가 견적을 내지 않는다.

추가 배치가 생긴 뒤 원주문의 수령 **날짜**를 바꿔 기존 배치를 재계산하지 않는다. 이후는 기존 날짜별 연장 접수를 이용한다. 같은 날짜의 시각 변경은 기존 경로를 유지한다. 연장은 현재 원래 짐+추가 배치 각각의 일요금 합계를 이어받고, 이미 확정된 기간·할인은 보존한다. 기존 환급·수령 권한을 확대하지 않는다.

## 기록과 안전성

- `luggage_bag_additions`는 추가 수량, 전후 수량·일요금, 배치 기간·일요금·장기 할인율·할인 전후 금액·등급 할인, JST 일자, 사유, 직원, 원자적 audit, 요청 해시를 불변 기록한다.
- 원주문 최초 청구·선결제·예정 보관일·장기 할인율과 기존 수납행은 변경하지 않는다. 청구 뷰가 추가분을 한 번 합산한다. 현재 물리 수량과 향후 연장의 배치별 합산 일요금만 검증된 기록으로 갱신한다.
- 수납 전에는 확정 미수납이 남아 수령이 차단된다. '실제로 받았다' 확인과 정확한 현금/QR 합계가 있어야 새 수납행을 만든다. 결제 공급자 청구·송금·가짜 환불은 없다.
- 견적 이후 주문·원장·환급 변경은 거래 내부의 전체 snapshot과 CAS로 다시 검사한다. 마감·동시 요청·다른 ID 경합은 원자적으로 거부한다. 같은 ID/동일 본문은 재실행하지 않고 기존 결과를 반환한다.
- 추가 짐과 수납은 한 D1 batch다. 수납을 나중에 하더라도 실제 receipt와 audit을 거래 안에서 검증하고, 무시된 SQL 쓰기를 탐지해 전체 롤백한다.
- 확정된 할인 환급 전후에도 총청구와 실제 수납에서 고정 할인을 중복 적용하지 않는다. 신규 환급 대기 중 추가 짐은 차단한다.
- 이후 연장은 합산된 짐 구성과 일요금을 복사한다. 기존 원수납과 추가분 청구는 그대로 보존한다.

## API·UI

원천 직원 화면: `/staff/orders/:id/bag-additions`, 기존 editor/admin과 같은 출처 POST만 허용한다.

서명된 원천 API: `/internal/luggage-orders/:id/bag-additions` GET/POST, `/preview`, `/collect`. HMAC 뒤 기존 활성 직원 매핑을 사용한다. 등록 스위치가 꺼져도 이미 등록된 동일 요청의 재확인과 실제 미수납 수납은 유지한다.

통합 어드민은 주문 상세에 전용 패널을 제공한다. 전역 MUTATIONS + LUGGAGE_OPERATIONS + BAG_ADDITIONS + 역할 + 기존 원천 직원 매핑 + source 스위치가 신규 등록에 필요하다. 기존 미수납 복구는 PAYMENT_STATUS gate를 쓴다. 전용 알바 Auth만 있고 기존 Luggage 직원 매핑이 없는 계정은 새로 권한을 부여하지 않는다.

브라우저는 계산한 금액을 보내지 않는다. 원천 견적만 표시하며 추가 청구와 최초 금액을 구분한다. 응답 불명 시 요청 UUID/본문을 세션에 보존해 같은 요청으로 확인하고 돈을 다시 받지 않도록 안내한다. 등록 이력의 ID로 완료를 재확인할 수 있다. 원천 쓰기가 성공하고 화면 갱신만 실패한 경우 성공 사실과 새로고침 안내를 분리한다.

## 배포·복구

운영시간에는 적용하지 않는다. 배포 전 latest source/런타임/마감·환급 작업을 재확인한다. 전용 스위치 기본값은 false다.

1. 기존 운영 스키마와 원장을 비공개 로컬 백업한다. 적용 여부와 schema hash를 검사해 이중 적용을 막는다.
2. `migrations/20261030_bag_additions.sql`만 원자적 D1 batch로 적용한다. **`src/schema.sql` 전체를 운영에 실행하지 않는다.** 기존 단건 승인 정책·트리거는 수정하지 않는다.
3. 현재 운영은 **F1**이다. Worker 배포는 반드시 `src/index.tsx` 진입점을 명시한다. 기본 `wrangler.toml`/기존 main 배포 workflow는 F0 진입점을 가리키므로 그대로 실행하거나 main push로 자동 배포하지 않는다. source Worker를 신규 등록 OFF로 배포하고 기존 모든 binding·flag·cron을 보존한다. 환급용 `LUGGAGE_PART_TIME_REFUND_ACTORS_ENABLED`와 별도 일반 알바 flag를 혼동하지 않는다. 기존 조회·환급·수령·마감 스모크 후 신규 기능을 검증한다.
4. 어드민을 REFUNDS profile 상태로 배포해 이전 asset을 보존한다. 검증 후 BAG_ADDITIONS profile로 올리면 기존 25개 flag를 보존하고 전용 flag 1개만 추가한다. source도 명시적으로 ON한다.
5. 원장·환급·마감 불변, 보호 규칙 보존, 런타임·asset·CI 증거를 기록한다. 첫 실제 직원 사용은 읽기 전용으로 사후 대조하며 허위 운영 수납으로 스모크하지 않는다.

실패 시 새 등록 스위치를 OFF로 내린다. 이미 기록된 추가분이 있으면 새 청구를 모르는 구버전 Worker/청구 뷰로 되돌리지 않는다. UI만 복구하더라도 새 청구를 인식하는 Worker와 수납 복구 경로는 유지한다. 불변 원장이나 migration을 파괴적으로 삭제하지 않는다.

## 검증

합성 자료만 사용한다. Worker 전체 회귀, 어드민 전체 회귀·typecheck/build, `scripts/bag-additions-local-e2e.mjs --run-local`(어드민에 위치), 기존 환급 D1/E2E를 수행한다. 새 로컬 D1 외 외부 요청은 차단한다. 운영 스키마의 비공개 단건 정책은 로컬 리허설에서만 읽고 소스·외부 검토에 넣지 않는다. 최종 수치·버전은 릴리스 증거를 따른다.

## 통합 대기

같은 기준 어드민 a8531a6 / Worker 237ffa2의 별도 알바 계정 변경과 단일 후보로 통합할 예정이다. 검증된 인계 패치를 받은 뒤에만 통합하며, 추가 짐 쓰기에도 일반 알바의 개별 `pt:<ERP UID>` actor·정지 상태·기능 스위치가 동일하게 적용되는지 검증해야 한다. 환급 전용 스위치가 다른 쓰기를 열면 안 된다. 인계 전 독립 운영 배포나 기본 F0 재배포를 하지 않는다.
